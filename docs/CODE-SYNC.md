# Code sync

A push to a connected GitHub, GitLab or Bitbucket repository updates a **review branch** of the model from the code. Diagrams that
show changed elements are refreshed, the differences are highlighted, and an owner or editor accepts all or some of the
changes into `main`.

## How code maps to the model

The C# reader (`Meridian.Serialization.CodeSync.CSharpCodeReader`) parses every `.cs` file of the commit into one Roslyn
compilation, so types resolve across files. It skips generated code (`obj/`, `bin/`, `*.g.cs`, `*.g.i.cs`,
`*.Designer.cs`, `*.AssemblyInfo.cs` and files that start with an `<auto-generated>` comment). Types from NuGet packages
or other assemblies are not resolved. They keep their names as written in the code, and Meridian creates no relationship
for them. If a file has syntax errors, Meridian reads what Roslyn can recover and adds a warning. Reading stops after
50,000 types, skips files over 2 million characters and stops when the files together pass 200 million characters. Each
limit adds a warning.

`Meridian.Core.CodeSync.CodeModelMapper.Apply` then writes the result into the model as SysML v1 structure, in **one
undo step**:

| Code | Model element | Notes |
|---|---|---|
| repository | Package `CodeSyncOptions.RootPackage` (default `Code`, `A::B` for nesting) | created if missing; never removed |
| namespace `Sat.Power` | nested Packages `Sat` › `Power` | symbol `ns:Sat.Power`; removed once empty |
| namespace dependencies | «use» Dependency between the packages the package overview shows | symbol `pkgdep:Sat.Comms->Sat.Power`, aggregated from the type relationships between them; `code.cycle = true` (and a note in the documentation) when part of a cycle; architecture checks ignore them like every code-made element |
| class, struct, record | Block | nested types are owned by their outer block |
| interface | InterfaceBlock | nested types of an interface go to the namespace package |
| enum | Enumeration with EnumerationLiterals | |
| field / property typed by a scanned class, struct or record | Property (part) typed by the block + Composition | multiplicity `*` for arrays, `List<T>`, `IEnumerable<T>`, dictionaries (value type) …; `0..1` for `T?`; otherwise `1` |
| field / property typed by a scanned interface | Property (reference) typed by the interface block + Association | |
| field / property typed by a scanned enum | Property (value) typed by the enumeration | |
| any other field / property | Property (value) with the C# type as text (`double`, `List<int>`) | |
| method | Operation, signature `(a : int, out b : string) : ReturnType` | one operation per overload; `in` is implied, `out` / `inout` (C# `ref`) are written; an untyped parameter is just its name; no signature for a parameterless method returning nothing |
| abstract class / abstract method | `isAbstract = true` on the block / operation | interface operations are not flagged |
| static field, property or method | `isStatic = true` on the property / operation | the metamodel has no static flag, so the UML attribute name is used |
| doc comment on a member | documentation of the property / operation | only written when the code has one |
| base class / base interface | Generalization | |
| implemented interface | Realization | |
| scanned type used in a body, parameter, local, `new`, static call or return type | Dependency | only with `IncludeUsageDependencies`; none when a part, reference, generalization or realization already links the pair |

Members that are not `public` are skipped unless `IncludeNonPublic` is set. A skipped member still counts as a usage
(Dependency) when its type is one of the scanned types.

**Collapse common root namespace** (repository setting, on by default, `CodeSyncOptions.CollapseRootNamespace`): when every
namespace starts with one segment, and that segment is named like the model package (case-insensitive) or no type is in
the global namespace, that segment gets no package. Its sub-namespaces and its own types go straight into the model
package, so a repository whose package and root namespace are both `Meridian` reads `Meridian › Core`, not
`Meridian › Meridian › Core`. Namespace symbols stay the full namespace (`ns:Meridian.Core`), so a project synced before the
setting (or with it toggled) is migrated on its next sync by moving packages: element ids, diagrams and hand-made content
stay, and anything else the old `Meridian` package held moves into the model package before the empty package is removed.

Validation rule MER-002 (unique sibling names) tells operations apart by their parameter types, as UML does: overloads
are fine, only two operations with the same name and the same parameter directions and types are reported.

Every element and relationship that code sync creates carries `code.symbol`, `code.file`, `code.line`, `code.repo` and
`code.commit`. Symbols are fully qualified with the generic arity (`Sat.Power.Battery`, `Sat.Box`1`). Members use
`Type.Member` and operations use `Type.Method(int,List<string>)`: the parameter types as written, whitespace removed, `?`
for an untyped parameter. Relationships use `gen:A->B`, `real:A->B`, `comp:A->B`, `ref:A->B` and
`dep:A->B`.

On every later sync:

- Meridian matches elements by `(code.repo, code.symbol)` and changes only the fields that code sync owns: name, type,
  multiplicity, visibility, signature, documentation (written only when the code has an XML `<summary>`) and the
  `code.*` keys. Stereotypes, tagged values, hand-made elements and hand-made relationships stay as they are.
  `code.commit` is set on each element that was created or changed. When only `code.file` or `code.line` changes, the
  field is updated but the element is not reported as changed.
- If a block's owner was moved by hand, or its namespace changed, Meridian moves it back into its namespace package.
- A type that moves to another namespace gets a new symbol. Meridian treats it as a move, not a delete plus a create,
  when exactly one type disappeared and exactly one appeared with the same kind and the same name in its namespace. The
  element keeps its id, diagrams and relationships. Its members and code relationships are re-keyed.
- A changed kind (for example a class that becomes an interface) replaces the element.
- When code disappears, Meridian deletes the element (`RemoveDeleted`, the default). The element is only marked
  `code.removed = true` when `RemoveDeleted` is off, or when the element owns a diagram, owns hand-made elements, or has
  a hand-made relationship. Code sync never deletes a diagram. A marked element is unmarked if its code comes back.
- Running the same code twice changes nothing: the second `Apply` returns an empty `CodeSyncChanges` and adds no undo
  step.

### Operations from earlier versions

Earlier versions of code sync made one `Type.Method()` operation per method name. On the next sync, Meridian keeps that element and
re-keys it to the first overload (in declaration order); the other overloads are added. More generally, when exactly one
operation of a method name no longer matches the code and at least one overload of that name is new, the existing operation
is updated in place instead of being deleted and created again. A changed parameter type therefore keeps the operation's
id, diagrams, stereotypes and hand-made content.

### Choosing the language

A connection's `Language` is `auto` (the default for new connections), `csharp`, `typescript`, `java` or `python`. `auto`
gives each file to the reader for its extension and merges the results; the host then fetches only the files that reader
handles (for TypeScript also its project files: tsconfig, package.json, pnpm-workspace.yaml). Existing connections keep
the language they were created with.

The TypeScript, Java and Python readers are hand-written, tolerant parsers: they run no Node.js, JVM or Python process and
never fail on code they do not understand. A part they cannot parse is skipped with a warning
(`path: N parts could not be parsed (first at line L …)`), and the rest of the file is read. They apply the same limits as
the C# reader (50,000 types, 2 million characters per file, 200 million in total). Output is deterministic: types are sorted
by symbol and members are in declaration order. Usage dependencies come from names in signatures, initializers and bodies
that resolve to a scanned type. Type parameters are never resolved as types. Collections (`List<T>`, `T[]`, `list[T]`,
`Map<K, V>` …) map to multiplicity `*`, and optional values (`T | null`, `x?: T`, `Optional[T]`, `Optional<T>`) map to
`0..1`.

#### TypeScript

| Code | Model |
|---|---|
| file `src/power/battery.ts` | package `src` › `power` (folders become packages; the file itself does not) |
| `namespace A.B { … }` / `module A { … }` | packages `A` › `B` below the folder packages |
| `class` (`abstract class`) | Block (`isAbstract`) |
| `interface`, `type X = { … }`, `type X = A & { … }` | InterfaceBlock (the named parts of an intersection are generalizations) |
| `enum`, `const enum` | Enumeration |
| property, `get` / `set` accessor, constructor parameter property (`constructor(private x: T)`) | Property; `#x` and `private` are private |
| method, overload signatures | Operation per overload signature (the implementation behind overloads is not listed again) |
| `extends` / `implements` | Generalization / Realization |

Symbols are `folder.path.Name` (`src.power.Battery`). Names resolve through the file's declarations (including enclosing
namespaces), imports (named, default, `* as ns`, `import type`, `import X = require(…)`, inline `import("./x").X` types),
re-exports (`export * from`, `export * as ns from`, `export { A as B } from`, `export { default } from`,
`export { A as default }`, `index.ts` barrels) and the declarations of script files (files without imports or exports are
global). Decorators are ignored, `node_modules/` is skipped, and union type aliases (`type Mode = "a" | "b"`) are not types.
A property without a type annotation takes its type from `= new X(…)`.

**Module resolution.** The reader also reads the project files that steer `tsc`'s module resolution: `tsconfig*.json`,
`jsconfig*.json`, JSON files in a shared config package's folder (`packages/tsconfig/base.json`,
`packages/typescript-config/nextjs.json`), every `package.json` and `pnpm-workspace.yaml` (never from `node_modules/`).
Each source file uses the nearest `tsconfig.json` (else `jsconfig.json`) above it. A specifier resolves, in order:

1. relative (`./x`, `../x`), with `.js` / `.mjs` written for `.ts` / `.mts`, and `index.ts` for a folder; when that fails,
   through `compilerOptions.rootDirs` (the root folders merge into one);
2. `compilerOptions.paths`: an exact pattern wins, then the pattern with the longest prefix before its `*`; the
   substitutions are tried in order, relative to `baseUrl`, or to the config that declares `paths` when there is none;
3. `compilerOptions.baseUrl`;
4. a **workspace package** by name (`@acme/ui`, `@acme/ui/gauge`): the packages are the folders matched by the root
   `package.json` `workspaces` (an array or `{ "packages": [...] }`) or `pnpm-workspace.yaml` `packages` (globs with `*`, `**`,
   and `!` exclusions). The package's `exports` (subpaths, `./*` patterns, conditions in the order `types`, `typescript`,
   `source`, `import`, `module`, `default`, `require` …), else `types`, `typings`, `source`, `module` or `main`, else
   `src/index.ts`, names the entry. Built paths map back to the source when only the source is in the snapshot:
   `./dist/index.d.ts` → `src/index.ts`, `./dist/components/*.js` → `src/components/*.ts` (`dist`, `build`, `lib`, `out`,
   `esm`, `cjs`, `types` …);
5. without a config: `@/x` and `~/x` → `src/x`, and `src/x` from the repository root.

`extends` follows relative paths (with or without `.json`), arrays (later entries win) and package names of configs in
the snapshot (`@acme/tsconfig/nextjs.json`, or `@acme/tsconfig` → its `package.json` `tsconfig` field or
`tsconfig.json`). `${configDir}` is the folder of the config the file uses. Anything else (a package in `node_modules`,
which is never scanned) is **external**: it makes no relationship or dependency, and its type keeps a clean name
(`logger: Logger`, `x: import("pino").Logger` → `Logger`). A config that is not valid JSON adds a warning and is ignored;
`extends` cycles are cut. This covers Nx (`tsconfig.base.json` paths), Turborepo / pnpm, npm and Yarn workspaces.

#### Java

| Code | Model |
|---|---|
| `package com.acme.rover;` | packages `com` › `acme` › `rover` (the package, not the folder) |
| `class`, `record`, `enum`, `interface`, `@interface` | Block, Block, Enumeration, InterfaceBlock, InterfaceBlock |
| nested (static) class | Block owned by the outer block (`IsStatic` in the code model) |
| field (each declarator of `int a, b;`), record component | Property; package-private is `package` visibility |
| method, constructor | Operation per overload; constructors are not listed; `default` / `static` interface methods are kept |
| `extends` / `implements` | Generalization / Realization (an interface's `extends` is a generalization) |
| enum constants | EnumerationLiterals |

Symbols are `package.Outer.Inner`; generics show in the name (`Source<T>`), not in the symbol. Names resolve like javac:
nested types of the enclosing types (and of their scanned base types), single-type imports (also of nested types), the same
package, on-demand imports (`.*`), then fully qualified names. `target/`, `build/generated…`, `module-info.java` and
`package-info.java` are skipped. Javadoc gives the text before the first block tag, without HTML tags.

#### Python

| Code | Model |
|---|---|
| module `src/lander/power/battery.py` | packages `lander` › `power` › `battery`: folders from the topmost folder with `__init__.py`; without any `__init__.py` the whole folder path is used |
| `class X:` | Block |
| class based on `Protocol` or `ABC`, or with `metaclass=ABCMeta` | InterfaceBlock; subclasses realize it |
| class based on `Enum`, `IntEnum`, `StrEnum`, `Flag`, `IntFlag` | Enumeration; `NAME = value` are its literals |
| annotated class attribute, dataclass field | Property (`ClassVar[…]` is static) |
| unannotated class attribute | static Property, type inferred from the value |
| `self.x = …` / `self.x: T = …` in `__init__` | Property; the type is the annotation, the hint of the parameter assigned, a class call `Battery(…)`, or a literal's type |
| `def` | Operation (without `self` / `cls`); `@staticmethod` and `@classmethod` are static; `@abstractmethod` is abstract; `@overload` signatures are the overloads |
| `@property` | Property typed by its return hint |
| `_x` / `__x` | protected / private |

Dunder methods (`__init__`, `__repr__` …) are not operations. The docstring's first paragraph is the documentation.
Names resolve through enclosing classes, the module, imports (absolute, relative, `as` aliases, `from x import *`),
re-exports in `__init__.py` and imports inside functions. String annotations (`"Battery"`) and `Optional`, `Union`,
`X | None` are understood. Virtual environments, `site-packages` and `__pycache__` are skipped. A class that only inherits
from a scanned enum is not recognised as an enum.

### Where dependencies are used

Every reader also records **where** a type uses each scanned type it depends on, in `CodeType.DependencyLocations`: a
list of `CodeDependencyUse(Symbol, File, Line, Kind)`, where `Kind` is one of

| Kind | C# | TypeScript / Java / Python |
|---|---|---|
| `inherit` | a type in the base list | `extends` / `implements`, a Python base class |
| `field` | a field, property or event type; a record's positional parameter | a property / field type, a dataclass field, `self.x: T` |
| `param` | a parameter type | a parameter type (also constructor parameters) |
| `return` | a method, local function, operator or delegate return type | a return type |
| `new` | `new T()`, `new()`, `new T[n]` | `new T()`; Python `T()` (calling a class) |
| `call` | `T.Method()` | `T.method()` |
| `import` | — (C# imports namespaces, not types) | the import that binds the name, recorded only when the type also uses the target |
| `use` | anything else: locals, casts, `typeof`, generic arguments, `T.Constant` | anything else |

C# takes the locations from Roslyn's syntax tree (partial classes point at the file of each part); the other readers
from the tokens. When one line uses a target several ways, one entry is kept (`inherit`, `new`, `call`, `field`, `param`,
`return`, `import`, `use`, in that order). Entries are sorted by target symbol, file and line, so the output is
deterministic. To stay small on very large code (200,000 types and more), at most 8 uses are kept per (type, target),
the first lines in file order (`MaxDependencyUsesPerTarget` on each reader); `CodeType.OmittedDependencyLocations` counts
the rest per target. The output therefore grows with the number of dependencies, not with the number of uses. Code
stored before this existed reads back with no locations. The architecture checks use them to point at the lines that
break a rule ([ARCHITECTURE-CHECKS.md](ARCHITECTURE-CHECKS.md)); the model mapping does not.

## Behaviour from code

Besides structure, every reader reads **method bodies** into a small control-flow tree, `CodeMember.Body`
(`Meridian.Core.CodeSync.CodeBody`, in `CodeBodyContracts.cs`). Code sync turns those into **activity diagrams** and
**sequence diagrams**. The tree has one `CodeStatement` per statement, each with its source line:

| Kind | Holds |
|---|---|
| `Call` | receiver as written (`battery`, `this`, `Battery`), `ReceiverType` (the scanned type, when resolved), `Method`, `Operation` (the exact overload, C#), `Arguments`, `ArgumentCount`, `IsAwait`, `IsStatic` |
| `Create` | `new T(…)`; `Method` is the type, `ReceiverType` the scanned type |
| `Assign` | `Text` is the target; when the value is a call, the call fields hold it |
| `Return`, `Yield` | `Text` is the value; when it is a call, the call fields hold it |
| `Throw` | `Text` is the expression, `Method` the exception type created |
| `If` | `Text` is the condition, `Body` the then block, `Else` the else block (an else-if is one `If` in it) |
| `Switch` | `Text` is the subject, `Branches` the cases (`case 1, 2`, `default`) |
| `Loop` | `Loop` = `For` / `ForEach` / `While` / `Do`, `Text` the header (`b in batteries`), `Body` |
| `Try` | `Body`, `Branches` = catch clauses (label = exception type, "" for any), `Finally` |
| `Using`, `Lock` | `Text` is the resource, `Body` |
| `Other` | short text (`break`, `continue`, `i++` …) |

Calls of scanned types nested in a statement (conditions, arguments, LINQ lambdas) are listed in `Calls`, in evaluation
order. Texts are cut at 80 characters, and a method keeps at most 300 statements (nested ones and calls included); the rest
are counted in `CodeBody.Omitted` and drawn as a "+N more" action. A read keeps at most 2,000,000 statements in total
(`MaxTotalBodyStatements`); later bodies are left out with a warning, so memory stays bounded on very large code. Readers
take `ReadBodies = false` to skip bodies. Types also get `Attributes` (attribute, annotation and decorator names) and
`ExternalBases` (base types that are not scanned, such as `BackgroundService`), and members get `Attributes`. All of it is
optional: stored code models from before read back without bodies, and `CodeModelJson` writes the new parts without empty
lists or default values.

### How bodies map to the model

Generated behaviours live in a **Behaviour** package inside the namespace package of the method's type (it is created when
needed and removed when empty). Each behaviour carries `code.symbol` = `act:Type.Method(int)` or `seq:Type.Method(int)`,
`specification` = the operation's id (UML `Behavior.specification`; the metamodel lets a block own a behaviour, but not an
operation), `code.hash` and the other `code.*` keys. Nodes, flows and messages carry `code.key`, a stable key built from the
path of the statement (its parents and a slug of what it is, numbered among equal siblings), so inserting a statement keeps
the keys of all the others.

**Activity** (`CodeActivityPlanner`):

| Code | Activity |
|---|---|
| method start / end | initial node / activity final node |
| call (statement, assignment of a call) | action named `receiver.Method()`; field `operation` = the called operation when it resolves to a scanned type (a CallOperationAction) |
| run of other simple statements (assignments, creations, `++`) | one action named after the first, "… (+N)" |
| `if` / `else if` / `else` | one decision node, a branch per condition guarded by its text, `[else]`; a merge node (decision node) when more than one path continues |
| `switch` | decision with a branch per case (`[1, 2]`, `[default]`, `[else]` when there is no default) and a merge |
| `for`, `foreach`, `while` | decision guarded by the loop header into the body, a back edge to the decision, `[else]` out; `break` leaves, `continue` goes back |
| `do … while` | merge node, body, decision `[condition]` back to the merge, `[else]` out |
| `try` / `catch` / `finally` | the try block, then a decision `[ok]` / `[catch IOException]` into each handler, a merge, then the finally block (the metamodel has no exception handler or interruptible region, so a handler is a guarded branch) |
| `using`, `lock` | an action `using x` / `lock x`, then the body |
| `return` | (the call, if any, then) an activity final node |
| `throw` | an activity final node with «exception», named after the exception type (the metamodel has no flow final node) |

The diagram is laid out top to bottom: a decision's branches side by side below it, the merge below the longest branch,
loop bodies under their decision.

**Sequence** (`CodeSequencePlanner`): a `caller` lifeline sends the entry call (`Balance(rounds)`) to a lifeline of the
method's type. The body is followed depth first into the scanned types it calls, up to **3 levels** and **60 messages**
(`CodeSyncOptions.BehaviourLimits`); calls of an interface method follow its only scanned implementation.

| Code | Sequence |
|---|---|
| object called | a lifeline per receiver: named after the field, property, parameter or local (`charger : ICharger`), typed by its block; `this` calls are self messages; static calls go to a lifeline of the type |
| call | synchronous message `Method(args)`; an awaited call is an asynchronous message |
| non-void method (other object) | reply message named after the return type |
| `if` / `else if` / `else`, `switch` | `alt` fragment with an operand per branch, guarded (`opt` for a lone `if`); fragments without messages are left out |
| loop | `loop` fragment guarded by the header |
| `catch` | `break` fragment guarded `catch IOException`; the try and finally blocks are inline |
| deeper calls, recursion, the message cap | not followed; a comment on the diagram says so |

Calls to types that are not scanned (framework, packages) are not messages.

### Which methods get diagrams

Each repository connection has a **Behaviour diagrams** setting (under *Model*, `CodeRepoConfig.BehaviourDiagrams`):

| Setting | What happens |
|---|---|
| **Off** | nothing; existing behaviours are left alone |
| **On demand** (the default for connections made before the setting existed) | no automatic diagrams. *Generate activity from code* and *Generate sequence from code* on an operation that came from code (its context menu on the tree and the canvas, the Inspector's *Behaviour from code* section, and ⌘K with the operation selected) build one from the code the last sync stored for the connection (the architecture check keeps it, `ArchitectureStore`) |
| **Entry points** (the default for new connections) | activities for public methods with real control flow (at least one branch or loop, or at least 5 calls); sequences for entry points: endpoint methods (`[HttpGet]`, `[Route]`, `@GetMapping` …, or a body that calls `MapGet` / `MapPost` …), controllers and handlers (by attribute `[ApiController]`, by base type such as `ControllerBase`, `BackgroundService`, `IHostedService`, `IRequestHandler`, or by a name ending in Controller, Handler, Endpoint(s), Consumer, Worker, HostedService or Job), `ExecuteAsync` / `StartAsync` / `StopAsync` of hosted services, `static Main`, and public methods of types nothing else in their namespace calls that call into other scanned types. Tests are left out (`[Fact]`, `[Theory]`, `[Test]`, `[TestMethod]`, `test_…`, types named …Test(s)). At most **20 activities and 10 sequences per namespace and 300 in total** per sync; the busiest methods (branches and loops count three times as much as calls) come first, and a warning in the run says how many were skipped |
| **All public methods** | an activity for every public method with a body and a sequence for every one that calls a scanned type, at most 300 new ones per sync |

Every behaviour that exists is brought up to date on each sync, in any setting but Off, whether it was generated
automatically or on demand. The caps only limit new ones.

### Re-syncs, review and layout

- Running the same code again changes nothing: a behaviour whose `code.hash` (everything it says, without lines and
  positions) is unchanged is not touched, beyond keeping `code.file` and `code.line` current.
- When a method's body changes, its activity and sequence are updated **in place**: elements whose key still exists keep
  their id and are changed only where their name or guard changed; new statements add elements, gone ones are removed.
  The behaviour itself is reported as changed. In *Code changes* the behaviour, its nodes, flows and messages are listed like
  structure elements, and the diagram highlights them (green added, amber changed). *Show on diagram* opens a behaviour's
  own diagram.
- Layout: when nobody moved anything on a generated diagram since the last sync (`code.layout` holds a hash of the shapes'
  places), it is laid out afresh. Otherwise shapes keep the places people gave them; new shapes go to their planned place.
  Fragments and message heights of sequences are always recomputed.
- When the method disappears (on a full snapshot), its behaviours are deleted, or marked `code.removed` when someone added
  their own elements to them. Behaviour elements never appear on the structure diagrams code sync refreshes.
- The architecture checks ignore behaviours; they read only structure.

### Limits per language

| Language | Bodies read | Calls resolved through |
|---|---|---|
| C# (Roslyn) | everything above, accurately; expression-bodied members; local functions are skipped (their calls appear, unresolved); switch expressions and lambdas stay inside their statement | the semantic model: this, base, static, extension methods, fields, properties, parameters, locals, `var`, LINQ lambda parameters (the core library, LINQ and the collections are referenced); NuGet types are not resolved |
| TypeScript | class methods (not functions outside classes, not the implementation behind overload signatures, not arrow-function properties); `if`, `for` / `for…of` / `for…in`, `while`, `do`, `switch`, `try`, `return`, `throw`, `break`, `continue`, calls, assignments, `new`; statements without semicolons end at a line break | `this`, `this.field`, parameters and locals with a type annotation or `new T()`; `for…of` variables have no known type |
| Java | methods (not constructors, lambdas or anonymous classes as bodies); as TypeScript plus enhanced `for (T x : xs)`, `synchronized`, try-with-resources, multi-catch and `->` cases; method annotations | `this`, fields, parameters, locals declared with a type or `new T()`, plain calls of the type's own methods; class-level annotations are not read |
| Python | methods (not `__init__` and other dunder methods, not properties); `if` / `elif` / `else`, `for`, `while`, `try` / `except` / `else` / `finally`, `with`, `match` / `case`, `return`, `raise`, `yield`, single-line bodies after a colon; decorators as attributes | `self`, `self.attr`, annotated parameters, locals annotated or assigned `Class(…)`, `with Class(…) as x`; calling a class is a creation |

The hand parsers never fail on a body they do not understand: what they cannot place becomes an `Other` statement.

### Performance

Reading Meridian's own `src` (452 files, 1,419 types, 5,522 method bodies with 58,377 statements) took 4.0 s without
bodies and 5.9 s with them (1.45×); mapping with *Entry points* (217 activities, 83 sequences) took 0.6 s instead of
0.2 s, so a whole sync took 1.52× as long. A re-sync of the same code took 0.4 s and changed nothing. The packed code the
architecture check stores grew from 837 KB to 2.5 MB. Measure it with
`dotnet run -c Release --project benchmarks/Meridian.Benchmarks -- --code-sync src`.

## Reviewing code changes

### Where the changes go

Every connected repository has its own review branch, named `code-sync/<repository>` (for example
`code-sync/acme/sat-fsw`). The first push that changes the model creates it from `main`'s current head; later pushes
**accumulate** on the same branch until they are reviewed. If `main` moves on in the meantime nothing needs rebasing: the
accept is a normal three-way merge.

Each push that is applied:

- reads the pushed source files and maps them onto the branch's model (a push that only touches files no reader handles, or
  that maps to no model change, is recorded as *No changes* and creates no branch);
- adds newly created elements to the existing diagrams they belong on — a new block to the BDD of its package, a new part to
  the IBD of its block, a new child to a package or block drawn as a container — placed in free space below what is already
  there. Shapes people positioned never move (a container may grow to hold a new child);
- creates diagrams for new namespaces and blocks with the auto-diagrammer (a structure diagram per new package, an IBD per new
  block with at least two parts typed by scanned classes: a block whose only part is one class, or whose members are all
  framework, collection-of-value or interface typed, gets none, as its package's structure diagram already shows it. On
  Meridian's own repository this cut the IBDs from 377 to 171). The first sync, and any sync that adds namespaces while
  there is none, also makes one **package overview** (`<root> – package overview`, under the root package): the top-level
  namespaces, and the level below while that stays at 40 packages or fewer, with the derived «use» dependencies; those in a
  cycle are drawn red. Later syncs keep it in step in place (packages added and removed, dependencies drawn) without
  moving shapes, and a later Auto-diagram run updates it rather than adding another. Each repository connection has a **Create diagrams for new packages and classes** switch (on by
  default, under *Model* in its settings). The model root's `codeSync.autoDiagrams` field (`true` or `false`) overrides the
  switch when it is set, and the settings say so;
- commits the result on the branch as `Code sync: <short sha> <first line of the commit message>` (authored by the system);
- records a **sync run**: commit, link, author, message, status, summary, counts and the list of changed elements.

Anyone with the branch open sees the update at once. A push that only carries the changed files (not a full snapshot)
never deletes elements.

**Edits made while a sync runs are kept.** The sync maps the code onto a copy of the branch and records every change it
makes as replication operations (the same `ModelOp`s collaborators exchange). When someone has the branch open, those
operations are applied to the live session. Whatever people changed on the branch in the meantime stays, and they see the
sync's changes arrive like a collaborator's. With nobody on the branch, the result is written to the store; if the stored
head changed while the sync ran, the operations are replayed onto the new head instead of replacing it.

**A failed sync leaves nothing behind.** When a sync fails (or is cancelled) after it created a new review or preview
branch, that branch is deleted again and the failed run is recorded without a branch. An existing branch is never deleted.

## Git submodules

Repository archives (GitHub tarball, GitLab `archive.tar.gz`, Bitbucket `get/<sha>.tar.gz` and Data Center `archive`)
leave the code of git submodules out: a submodule is an empty folder in them. With **Include git submodules** on (the
default), every sync — pushes and pull request previews alike — also reads the submodules and merges their files into the
snapshot under the submodule path, so `libs/core/src/Battery.cs` maps like any other file. The code is in
`src/Meridian.Web/CodeSync/Hosts/Submodules.cs` (discovery, credentials, merge) and `SubmoduleHosts.cs` (pinned commits).

1. **Discovery.** After reading the archive, Meridian reads `.gitmodules` from it (always, even outside the folders to
   include). The reader is tolerant: quoted values, `#` / `;` comments, line continuations, the old
   `[submodule.name]` form; malformed lines are skipped. Each entry gives `path`, `url`, `branch` and `update`.
2. **Pinned commit.** The submodule is read at the commit the parent pins it to (its *gitlink*), never at a branch head.
   Meridian asks the host's API at the parent commit:

   | Host | How the pinned commit is read |
   |---|---|
   | GitHub | `GET /repos/{owner}/{repo}/contents/{path}?ref={commit}` → `{"type":"submodule","sha":…}` |
   | GitLab | `GET /projects/{id}/repository/tree?path={folder}&ref={commit}` → the entry with `"type":"commit"`, its `id` |
   | Bitbucket Cloud | `GET /2.0/repositories/{ws}/{repo}/src/{commit}/{folder}/` → the entry for the path whose type names a submodule, or a directory whose `commit.hash` is not the listed commit |
   | Bitbucket Data Center | `GET /rest/api/1.0/projects/{key}/repos/{slug}/browse/{folder}?at={commit}` → the child with `"type":"SUBMODULE"`, its `contentId` |

3. **Where it lives.** The URL is resolved to a host and repository path: `https://`, `ssh://`, `git://` URLs, scp-like
   `git@host:group/repo.git`, and relative `../lib.git` / `./lib` (git's rule: each `../` drops one segment of the
   parent's path on the parent's host). Bitbucket Data Center's `/scm/PROJECT/repo.git` is understood. User names and
   passwords in a URL are ignored and never shown.
4. **Credentials**, tried in order until one works:
   - a code-repo connection **in the same project** for exactly that repository (host and path) — its own token;
   - the connection's own token, when the submodule is on **the same host** as the connection;
   - **anonymous** access on `github.com`, `gitlab.com` and `bitbucket.org`, for public repositories.

   A token only ever goes to the API address of the connection it belongs to. A URL in `.gitmodules` never chooses where
   a request goes: requests go only to configured connections and to the fixed public API addresses, all through the same
   outbound address checks as every other integration (private networks only when the administrator allowed them). A
   submodule on any other host is reported as *no access*, without a request.
5. **Merge.** The submodule's archive is fetched at the pinned commit and its files are added under the submodule path.
   The connection's **Folders to include** apply to the merged paths: a submodule outside them is skipped, one partly
   inside is read only there. Submodules of submodules are followed up to **3 levels**; a repository that includes itself
   (directly or further down) is cut off as a cycle. At most 50 submodules are looked at per sync.

**Limits cover the whole snapshot.** The archive, file count, per-file size and total size limits of a sync (200 MB
compressed, 4 GB unpacked, 20,000 files, 2 MB per file, 500 MB of source) count the repository and all of its submodules
together. Going over any of them fails the sync, as it does for a single archive.

**Failures do not stop the sync.** A submodule that cannot be read (token without access, private repository on another
account, deleted repository, a path in `.gitmodules` with no gitlink at the commit) is recorded and logged; the sync
continues with everything else, and its summary ends with “(N submodules not read)”. The fix is usually a connection
for that repository in the same project, or a token that can read it.

**Settings** (per connection): *Include git submodules* (`IncludeSubmodules`, default on) and *Submodules to skip*
(`SkipSubmodules`, paths such as `vendor/big-library`; a nested one by its full path). `update = none` in `.gitmodules`
also skips a submodule. The connection lists the submodules of the last sync of its branch, each with its pinned commit
and a status: **fetched** (with the number of files), **skipped** (why), **no access** or **not found**.

**Bumps in Code changes.** The commits a repository pins its submodules to are kept on the model root, in the field
`code.submodules:<connection id>` (one `path@sha <compare link>` line each). Moving a submodule to another commit
changes that field, and *Code changes* lists it under **Submodules** as `libs/core 1a2b3c4 → 5d6e7f8`, with a
**Compare** link on GitHub, GitLab and Bitbucket, next to the element changes the new code caused. Accepting it moves
`main`'s pins forward; a new submodule shows as *added*, a removed one as *removed*. The pull request comment lists bumps
as rows of kind *Submodule*. Pins are recorded for skipped and unreadable submodules too, so their bumps still show.

**Where elements came from.** Elements mapped from submodule code carry `code.submodule` = `path@sha` next to
`code.file`. Like the file and line it is kept current on every sync, and a bump alone does not mark the element as
changed. The architecture checks read the same merged snapshot, so they cover submodule code too.

## Pull request previews

When a pull request (GitHub, Bitbucket) or merge request (GitLab) **into the followed branch** is opened, reopened or gets
new commits, Meridian syncs its head into a **preview branch** `code-sync/<repository>/pr-<n>`, created from `main`. The
name is shortened to fit the 60-character branch limit, keeping the `/pr-<n>` suffix. Pull requests into other branches
are ignored, and the connection's **Preview pull requests** switch turns previews off.

- The PR head gets the `meridian/model` commit status: `pending` while Meridian works, then `success` with the summary
  ("Model preview: 3 added, 1 changed") and a link to the preview, or `failure`. A preview never leaves a pending status,
  because nobody accepts it.
- With **Comment on pull requests** (on by default), Meridian keeps **one** comment on the pull request: the counts, the
  first 10 changes (kind, name, element kind, owner) and a link to the preview. Later pushes edit that comment in place.
  If someone deleted it, a new one is posted. The comment id is kept in the connection's settings.
- In Meridian the title-bar badge shows open previews as **PR #n**, next to *Code changes (N)* when the followed branch has
  changes to review. *Code changes* lists each preview under a **PR #n** heading. A preview is for looking only: its
  changes cannot be selected, accepted or rejected, and on `main` the diagram highlights leave previews out. Open the
  preview branch to see its highlights.

When the pull request is **merged**, Meridian deletes the preview branch and closes its runs. It does not carry the
preview's changes over: the merge is a push to the followed branch, and that push's full-snapshot sync brings the same
changes, worked out against the current `main`, to the review branch. That is simpler than moving the preview, and it is
always right, because the preview may be out of date with `main` or with what was finally merged. When the pull request
is **closed without merging**, the preview branch is deleted and its runs are marked rejected. If someone has the preview
branch open at that moment, the branch is kept (its runs are still closed) and can be deleted from the branch menu.

### The review

When a code-sync branch has changes waiting, the title bar shows **Code changes (N)** next to the branch picker. It opens
**Code changes**, a tab next to the diagrams (also on ⌘K “Code changes”, and in the *Code* ribbon group). The commit-status
link a git host shows opens the project on the review branch with this tab open
(`/?project=<id>&branch=<id>&panel=code-changes`).

Code changes lists, per review branch:

- the pushes waiting for review — short sha (linked to the commit), message, author, time and summary. Ticking a push selects
  all of its changes;
- the changes, grouped into **Added**, **Changed** and **Removed**, each with its kind, name and owner path. A changed element
  expands to show its field changes (before → after). The list is the *net* difference between the branch and what `main`
  last took from it, so a change a later push undid disappears;
- **Show on diagram** opens a diagram that shows the element (switching to the review branch for an element that only exists
  there) and selects it.

Filter by name, path or kind, tick changes (or **Select all**), then:

- **Accept selected** merges them into `main`. Changes you did not select keep `main`'s version and stay on the branch for
  later. If someone changed the same thing on `main`, the usual merge dialog asks which side to keep.
- **Reject selected** puts those elements on the review branch back to `main`'s version. A later push that still contains
  them brings them back (the code is the source of truth).

A push whose changes have all been decided is closed (*Accepted*, or *Rejected* when none were accepted). Only project
owners and editors can accept or reject; viewers can read the review.

### Highlights on diagrams

On a review branch, diagrams highlight what the code changed (toggle: the legend on the canvas, the *Code ▸ Highlight*
ribbon button, or ⌘K “Highlight code changes”; it is on by default when you open the branch):

| Change  | Drawn as |
|---------|----------|
| Added   | green outline |
| Changed | amber outline |
| Removed | a faded, dashed “ghost” at the place `main` has it, until accepted or rejected |

On `main` the same toggle outlines the elements a pending review would change or remove. The colours follow the theme's
status colours, so they read in light and dark mode.

### For integrators

- `ICodeSyncRunner.RunAsync(CodeSyncRequest)` (the git-host integration calls it after fetching files) returns a
  `CodeSyncOutcome`: `AwaitingReview` with the review link, `NoChanges`, or `Failed` with the reason. Runs of one project are
  serialized; review decisions take the same lock.
- `IPullRequestPreviews` (implemented by `CodeSyncRunner`): `RunPreviewAsync(request, n)` syncs into the preview branch,
  `ClosePreviewAsync(project, repo, n, merged)` deletes it, and `PreviewChangesAsync(project, repo, n)` lists its net
  changes for the pull request comment. `CodeSyncRunner.PreviewBranchNameFor` and `PreviewNumber` map between numbers and
  branch names; `CodeSyncReview.IsPreview` and `PullRequest` tell the UI.
- `CodeSyncReviewService.Accepted` is raised once per run when its last pending change is decided and at least one was
  accepted, with `(outcome, connectionId, commitSha)` — use it to update the commit status. `Rejected` is raised when all of a
  run's changes were rejected.
- `CodeSyncRequest.Submodules` lists the repository's submodule pins (`CodeSubmodulePin`: path, sha, compare link,
  fetched). The runner writes them to the model root (`CodeSubmodulePins.FieldKey`) and passes the fetched ones to the
  mapper (`CodeSyncOptions.Submodules`) for `code.submodule`. `CodeSubmodulePins.Bumps(before, after)` turns two field
  values into bumps. Callers that know nothing of submodules leave it empty; a partial push then leaves the pins alone.
- `IGitHost.ResolveSubmoduleCommitsAsync(commit, paths)` returns the gitlinks, and
  `IGitHost.FetchSnapshotAsync(…, SnapshotBudget, …)` reads an archive against a shared budget. Both have default
  implementations, so other hosts and test fakes keep compiling.
- Runs are stored in the `code_sync_runs` table (SQLite and PostgreSQL), one row per push, with the change list as JSON.
- The model root's `codeSync.rootPackage` field names the package code is mapped into. It overrides the connection's
  *Model package*, which defaults to the repository name. `codeSync.autoDiagrams` likewise overrides the connection's
  *Create diagrams for new packages and classes* switch.
- `CodeSyncEvents.RunCompleted` is raised with `(request, outcome)` after each run that did not fail (pull request
  previews included). The architecture check subscribes to it and posts its own `meridian/architecture` status
  ([ARCHITECTURE-CHECKS.md](ARCHITECTURE-CHECKS.md)).
