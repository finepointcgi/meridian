# Integrations

Meridian connects to issue trackers, syncs requirements with DOORS Next and Polarion, notifies other systems through
webhooks, and exposes requirements and model data
to other tools through OSLC and a read-only SysML v2 API. Project owners set integrations up with **Integrations
(issue trackers, webhooks)…** in the project menu.

## Issue trackers

| Tracker | Base URL | Project | Credentials |
| --- | --- | --- | --- |
| Jira Cloud (REST v3) | `https://your-site.atlassian.net` | project key, e.g. `MER` | Atlassian account e-mail + API token |
| Jira Server / Data Center (REST v2) | `https://jira.example.com` | project key | personal access token |
| Azure DevOps (work items) | `https://dev.azure.com/your-org` | project name | PAT with *Work Items: read & write* |
| GitHub Issues | `https://api.github.com` or `https://ghe.example.com/api/v3` | `owner/repo` | fine-grained token with *Issues: read & write* |

Optionally set the issue type for new issues (default `Task`). **Test connection** checks the credentials and that
the project is reachable. Base URLs must be `https://`.

Tokens and secrets are encrypted before they are stored, are only decrypted to call the tracker, are never logged and
never sent back to the browser (the dialog shows "••• set"; leave the field empty to keep the stored value). They are
encrypted with the server's Data Protection keys, so keep `Meridian:KeysPath` on persistent storage.

### Linked issues

The inspector's **Linked issues** section on every element offers:

- **Link issue**: type a key (`MER-12`, `#12`, `4711`), paste the issue's URL or search by text;
- **Create issue from this element**: the title is the element name (requirements: `REQ-001 Name`) and the description
  holds the requirement text, documentation, qualified name and a deep link back to Meridian;
- the key, title, status and assignee of each link, with **↻** to refresh it.

Select a package (or the model) to **Push N requirements as issues…**: one issue per requirement below it that has no
issue in that tracker yet, as one undo step. **Sync status** in the Integrations dialog refreshes every link of the
project. Links are stored on the element, so they are versioned, exported and replicated like any other edit.

## Webhooks

Integrations dialog → **Webhooks**: a payload URL, a secret (generated by default and shown only until saved), an
optional event filter and an enabled switch. **Send** posts a `ping`.

| Event | When |
| --- | --- |
| `version.committed` | a version is committed (`number`, `message`, `author`) |
| `element.changed` | model edits, batched: 5 s after the last edit or 30 s after the first (`count`, `elements[]` with id, change, name, kind) |
| `comment.changed` | a comment is added, resolved / reopened or deleted |
| `ping` | the Send button |

Each request is a JSON `POST` with headers `X-Meridian-Event`, `X-Meridian-Delivery` (the same for every retry) and
`X-Meridian-Signature-256: sha256=<hex HMAC-SHA256(secret, body)>`. Verify the signature with a constant-time compare:

```python
expected = "sha256=" + hmac.new(secret.encode(), request.body, hashlib.sha256).hexdigest()
ok = hmac.compare_digest(expected, request.headers["X-Meridian-Signature-256"])
```

A 2xx response is success. Network errors, timeouts (10 s), 408, 429 and 5xx are retried after 10 s, 1 min and 5 min;
other 4xx are not. The latest 50 attempts are shown under *Recent deliveries*.

## DOORS Next and Polarion

**Integrations… → Requirements tools** connects a project to IBM DOORS Next or Siemens Polarion. Project owners add
connections; editors can sync.

* **DOORS Next**: enter the RM application URL (`https://jazz.example.com/rm`) and sign in with Jazz form login,
  HTTP Basic or an app password. **Browse projects** and **Browse modules** pick what to import.
* **Polarion**: enter the server URL and a personal access token. **Browse projects** and **Browse documents** pick
  what to import; work items of type `requirement` are imported by default.

**Sync now** creates or updates Meridian requirements. Each one keeps the tool's id, URL and revision (attributes
*External ID*, *External URL*, *External revision*). When the tool changes a requirement, Meridian updates it and its
trace links become suspect. When both sides changed it, a dialog shows the differences and you choose which version
to keep. Syncs can also run on a schedule (every 15 minutes to daily).

Optionally, Meridian publishes its «satisfy», «verify» and «trace» links back: as OSLC links in DOORS Next, and as
linked work items or linked OSLC resources in Polarion. This is off by default and needs a team server.

## OSLC provider (server)

A team server is an OSLC 2.0 provider for requirements (RM) and model elements (AM), so ALM tools that speak OSLC can
query, select, create and preview Meridian items.

| Resource | URL |
| --- | --- |
| Root services | `/oslc/rootservices` |
| Service provider catalog | `/oslc/catalog` |
| Service provider | `/oslc/projects/{projectId}/provider` |
| Requirements (query, and POST to create) | `/oslc/projects/{projectId}/requirements` |
| Model elements (query) | `/oslc/projects/{projectId}/resources` |
| Selection dialog | `/oslc/projects/{projectId}/selector` (add `?type=resource` for model elements) |
| Creation dialog | `/oslc/projects/{projectId}/creator` |
| Resource shapes | `/oslc/shapes/requirement`, `/oslc/shapes/resource` |

Responses are RDF/XML, Turtle or JSON-LD, chosen by `Accept`. Queries support `oslc.where` (`and`, comparisons,
`in`), `oslc.select`, `oslc.orderBy`, `oslc.prefix`, `oslc.searchTerms` and paging. Link hovers in other tools show a
preview through OSLC Compact. Authenticate with an API token; OAuth 1.0a (Jazz "friends") is not supported, so in IBM
ELM link to Meridian items by URL.

```sh
curl -H "Authorization: Bearer mrd_…" -H "Accept: text/turtle" \
  "https://meridian.example.com/oslc/projects/<id>/requirements?oslc.where=dcterms:identifier=%22REQ-002%22"
```

## SysML v2 API (server, read-only)

`/api` serves a read-only subset of the OMG Systems Modeling API: `GET /api/projects`,
`/api/projects/{id}/commits`, and the elements (`…/commits/{commitId}/elements`, `…/elements/{elementId}`) and root
elements (`…/commits/{commitId}/roots`) of a commit.

## API tokens

Both APIs accept the browser session, HTTP Basic (username and password) or a **personal access token**. Create tokens
in **API tokens…** (avatar menu); a token is shown once. Send it as `Authorization: Bearer mrd_…`, or as the Basic
password for tools that only speak Basic. Only a hash is stored, revoked tokens stop working immediately, and a token
has its owner's access to every project.
